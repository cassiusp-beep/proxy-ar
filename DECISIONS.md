# Decisions

Each entry says what was decided, what else was considered and why it lost, and (from 014 on) whether the choice was familiar or new for this project, so a later reader can tell a choice from a habit. Superseded entries stay, with a note pointing to what replaced them.

**How this trail was written.** Entries 001–013 were written by the orchestrating session, which also did the work, with no independent review. They don't record familiar-or-new. From 014 on, entries are written by the documenter role from the files and the orchestrator's account (see 015). Device numbers behind 011–018 are in [docs/AR_ALIGNMENT_PLAYBOOK.md](docs/AR_ALIGNMENT_PLAYBOOK.md) §6.

## 001 · World anchor at marker lock (Phase 1)
When the marker is locked, PROXY adds a plain `ARAnchor` at that pose and hangs content from it, so content stays when the marker leaves view.
- Rejected: parenting content to the image anchor. The content follows the marker, jitters, and has no stable pose once the marker is out of view.
- Rejected: continuous image tracking with smoothing. It needs more code and still fights world tracking when the marker is partly occluded by terrain.
- Escape hatch: the debug panel's Sync button drops the anchor and locks again.
- **Updated (011, 014):** the lock is no longer the first detection's one-shot pose. While unlocked, ARKit tracks the markers (`maximumNumberOfTrackedImages = 2`) so their poses can be averaged; once locked it drops to 0. The world-anchor design itself is unchanged.

## 002 · Offset lives on a single `offsetEntity`
MARKER_TO_ORIGIN, yaw and scale are applied to one intermediate entity between the anchor and the content. The sliders, nudge pad and fit edit it live, and the placeholder and city.usdz share it unchanged.

## 003 · Cartoon look by material replacement at load time
Every material on city.usdz is replaced with a saturated `SimpleMaterial` (roughness 0.85, non-metallic), or with `UnlitMaterial` if `ContentLoader.useUnlit` is set. Colors are chosen by name keyword (road, tree, water, roof, window) first, then by a stable FNV hash, so they don't reshuffle between launches.
- Rejected: restyling in Blender/Reality Composer. It's faster to iterate in code while the model is still changing.

## 004 · Generated marker, hand-written Xcode project
Markers are generated by `tools/make_marker.py` with fixed seeds (1848 for CalibrationMarker, 2030 for CalibrationMarkerRight; see 014), so reprints match the bundled reference images. `tools/make_marker_pdf.py` lays a marker out on a US Letter page at exactly 50 mm with a check ruler. The project file is hand-written with an Xcode 16 synchronized folder (no xcodegen dependency). Deployment target is iOS 26, iPhone-only, landscape left/right (see 007). The only device we target is iPhone 17 Pro Max, so there is no fallback for older hardware or iPad layouts.

## 005 · LiDAR scene reconstruction on
The session runs `sceneReconstruction = .mesh`, which the iPhone 17 Pro Max's LiDAR always supports. It gives steadier world tracking around the terrain model, and the debug panel's "Show mesh" toggle draws the scanned surface so the slab can be aligned against real geometry, not by eye.

## 006 · Mesh occlusion on by default (superseded by 007)
Real terrain hides virtual content behind it (`sceneUnderstanding.options.occlusion`), because content, such as the overlay of the intended city, moves behind physical features. The LiDAR mesh is coarse (a few cm), so geometry sitting right on the terrain surface can lose its base or flicker at the contact line.
- **Superseded:** 007 made the exact pin model the default occluder. LiDAR occlusion is now the debug panel's "LiDAR occlusion" toggle, off by default.

## 007 · Content built from the Rhino file, measured from the pin origin
`city.usdz` (`TERRAIN_GRAY` banded by elevation, plus `FIGURES_MARBLE`) and `pins_occluder.usdz` (`PINS_FULL`) are exported by `tools/export_models.py`. Coordinates are relative to `PINS_ORIGIN`, converted to meters and Y-up, so the only calibration value is MARKER_TO_ORIGIN.
- **Footprint:** The brief's 304.8 mm / 40 × 40 pins was the first, 2.08×-scale `pins.py` run. The printed pins (and the base pocket built around them) are 158.6 × 146.4 mm, 43 × 40, so the app uses the real values.
- **Marker:** 50 mm, because the final `base_part_5` has 1 mm corner guides for a 50 mm marker. The brief's "largest square with 5 mm margin" rule would give about 90 mm, which would rest on the guides. (A bigger single marker was later set aside for the same reason; the diorama gets a second marker instead, see 014.)
- **Occlusion:** The exact pin model replaces LiDAR mesh occlusion as the default (LiDAR stays as a toggle). The mesh is a few cm coarse and clipped the city everywhere it touches the pins. The occluder is lowered 1.5 mm to avoid z-fighting with the coincident pin-top surface. (Narrowed by 010: it only acts with the city hidden.)
- **Orientation:** Landscape only, because the phone sits horizontally in a Backbone-style controller (brief §2.4).

## 008 · The Field Unit's front is Rhino +X (marker yaw −90°)
`diorama.py` faces every facade "toward the viewer (+X)", and the base parts agree: front-left holds the marker (low Y), front-right holds the inputs (high Y). With the marker read upright from the front, its top edge points to Rhino −X, so the content is yawed −90° relative to the marker, and MARKER_TO_ORIGIN = (−0.0346, −0.0062, −0.2466). The first version assumed the front was −Y; that would have rotated the city 90° on the pins.

## 009 · NPCs walk the diorama's declared paths
NPCs are a RealityKit ECS component + system, children of the content so calibration moves them too. They walk path polylines and strolls; heights come from a 0.5 mm heightfield of TERRAIN_GRAY (`terrain_height.bin`, which the drone will reuse for terrain clearance). Strolls are rejected if any 1 mm step climbs more than 0.8 (walls, roof edges).
- **Paths:** `diorama.py` routed and carved the paths but didn't save them. A read-only `RUN_MODE = "paths"` was added to it to write `paths.json`. Until then, routes are rebuilt by re-running its A* on the finished terrain with a pull toward smooth ground (the carved beds are the only grain-free areas). Checked against the logged path figures: FRONT-LOW and LOW-MID2 match within 1 mm; LOW-MID is 31 mm off, and MID-HIGH is half the logged length.
- **Role:** Most NPCs are ambient townspeople; missions will mark a few as targets (phase 3), and the Prestige thermal view will render them all alike.

## 010 · Two physical setups; the pin occluder only acts when the city is hidden
The first device test (2026-10-26) used the diorama/trophy print with the marker on the table in front of it. The city appeared correctly oriented but displaced, because the offset assumed the Field Unit's sync dock. The debug panel now switches between **Field Unit** (marker in the dock) and **Diorama** (marker on the table against the marble base). Each has its own measured constant. The diorama shares the pins' Rhino coordinates, so the same content and origin apply.
- **Diorama placement (superseded by 014):** one marker, paper trimmed to the black border, top edge against the base's front face, left edge in line with the base's left side. 014 adds a second marker at the front-right corner; the left one stays where it was.
- **Occluder:** It carved the city into stripes: pin side walls hid the terrain behind them from oblique views. The overlay is meant to replace the physical model, and it's opaque, so it already hides NPCs behind ridges. The pin occluder now runs only in the Field Unit setup with the city hidden.

## 011 · Leveled lock: trust the marker's position and heading, not its tilt
On device the city slid off the model when the phone was tilted to a new viewpoint. A 50 mm marker's estimated tilt can be off by a degree or more, and content up to 20 cm away and 13 cm tall swings millimeters per degree. The models sit on a level table, so the lock now takes up from gravity (ARKit's world Y) and only position plus heading from the marker. Each lock logs the tilt removed.
- **Superseded in part (017):** the lock used to snap its height to the LiDAR table plane (if within 15 mm). Since 017 the height comes from the markers and the plane is only logged. Leveling and averaging are unchanged.
- **Result:** over eight logged locks, leveling removed 1.3–3.9° of marker tilt per lock, which is 5–14 mm at the far side and peak. Confirmed necessary.
- **Averaged lock (added after scans 2a/2b):** a single frame's heading was off by about 0.8° on one lock, reproducibly. `MarkerSampler` now tracks the marker while unlocked and averages 30 samples (circular mean of heading with outliers dropped, per-axis median of position; locks with at least 6 after 2 s). Within-lock spread came out tiny: heading ±0.05–0.07°, position ±0.6–0.8 mm. Rejected: a bigger marker (the dock's guides are 50 mm, 007).
- **Limit found:** averaging removes jitter within a lock, not a bias that changes from lock to lock with the viewpoint. That is what 014 addresses.
- **Resolved (017):** one lock snapped the height by +10.4 mm, and the fit can't see height errors (012). The analyst's snap hypothesis (016-A) was tested in the first two-marker session and the snap was removed.

## 012 · LiDAR fidelity fit
A guided scan ("Start scan" in the debug panel) collects high-confidence LiDAR depth-map points that land on the model, with a coverage bar, and fits at 75% coverage or on "Fit now". It solves (Gauss-Newton, Huber weights) for the shift and yaw that put them on the Rhino terrain heightfield. It reports scan-to-model RMS before and after, so it doubles as a pre-demo fidelity check. "Apply fit" folds the correction into the offset, and "Print values" keeps it. Tilt is not solved for (see 011). The outer 4 mm is ignored (edges, back wall, base).
- **Depth map, not scene mesh:** the first version used the scene mesh. Its room-scale triangles left too few points on a 15 cm model for the fit to run, so it switched to the per-frame depth map (256 × 192, every third frame, every second pixel). Scan, fit and failure messages all go to the console.
- **Height is a nuisance term:** the first full scan (2026-10-26) had 30,000 points, 76% coverage, and fit 9.9 → 3.7 mm, but it lowered the city 7.1 mm, below the tabletop, and paid for it with 1.8° of yaw and a sideways slide (visible as a gray strip on the left). LiDAR depth on the small matte model reads a few mm deep. Height is now never fitted: a vertical term absorbs the depth bias (reported as "LiDAR bias … ignored"), and only x, z and yaw are applied. The "before" RMS also removes the bias, so the comparison is fair.
- **Fit yaw is not repeatable:** two scans on the same averaged lock gave +2.35° and +0.80°, while the marker's own heading jitter was ±0.07°. The fit's position is the trustworthy part. (Note: "Apply fit" in the code still applies the yaw; the playbook says to use the fit for position only.)
- **Saved forward offset, then retired:** four scans over two locks agreed on x +3.7, +2.5, +3.2, +3.8 mm (mean 3.3 ± 0.6), so with the user's approval DIORAMA z was changed from −0.2028 to −0.2061 (city 3.3 mm toward the back). In the next session the user had to nudge the city by 10.4 mm by hand (reported by the orchestrator; not yet in the measurements log). The reasoning was that the error moves from lock to lock, so a constant can't hold it, and 014 reverted the constant to the geometric −0.2028. The alignment-analyst has since questioned that (016).
- Rejected for now: running the fit after every lock (see 014's alternatives).

## 013 · Hand occlusion by person segmentation
`personSegmentationWithDepth` is on (with scene reconstruction), so a finger pointing at a building covers the cartoon city where it is in front of it. If the session ever fails with both enabled, it logs the error and reruns without segmentation. "Hand occlusion" in the debug panel turns it off (`disablePersonOcclusion`).

## 014 · Two-marker lock for the Diorama setup
*2026-10-26. Implemented; reviewer PASS; review fixes landed (checked in `MarkerLock.swift`); first device session 2026-10-26 (findings below). Not yet passing playbook §7.*

**Problem.** The Diorama lock used one 50 mm marker. Averaging (011) made each lock steady to ±0.07°, but locks still disagreed with each other by mm and 1–2°, depending on where the phone looked from. The model's far side is about 20 cm from the marker, so each degree of heading is about 3.5 mm there. The saved 3.3 mm correction (012) fixed one session and missed the next by 10.4 mm.

**Decision.** Two markers lie flush at the marble base's front-left and front-right corners: CalibrationMarker (left, unchanged) with its center at Rhino (207.8, 25.0), and the new CalibrationMarkerRight at (207.8, 121.35), 96.35 mm apart, with its right edge in line with the base's right side. Heading comes from the line between the two centers, and position from both.
- **Expected benefit, corrected.** An earlier draft of this entry claimed a heading "about 4× steadier". That overstated it: the baseline is 96.35 mm against a 50 mm marker, about 1.9×. The reviewer's Monte Carlo gave 0.97° RMS heading error with ±2 mm of independent noise per marker, no better than the single-marker problem this is meant to fix. So the gain depends on how ARKit's marker errors behave. If they are mostly common-mode (depth along the viewing ray, scale), both markers shift together, the pair's heading stays robust, and the error shows up as a spacing error instead. If they are independent per marker, two markers gain little. This is unknown until the first device session (playbook §7).
- `DIORAMA_MARKER_TO_ORIGIN` goes back to the geometric (−0.0250, 0.0075, −0.2028); the session-specific 3.3 mm correction is retired. (Possibly premature; see 016.)
- **Built-in check:** each lock logs the measured spacing against 96.35 mm and warns if the markers look misplaced, swapped or misprinted.
- If only the left marker is seen, the app falls back to a single-marker lock and says so.
- Applies to the Diorama setup only. The Field Unit keeps its single dock marker for now.

**Review.** Reviewer verdict: PASS. Fixes, now in the code (the first four ran in the device session):
- gross-error rejection: fall back to a single-marker lock when the two-marker result is off by more than 20° or 15 mm;
- at least 15 samples per marker before locking (currently 6);
- richer per-lock logging;
- image detection turned off after lock;
- a "Re-lock (keep world)" button;
- a print-scale diagnostic.

**Alternatives.**
- *Offered to the user:* (a) auto-fit after every lock: LiDAR, about 1–2 mm, but needs a scan each session; (b) both two markers and auto-fit; (c) two markers. The user chose (c).
- *Tried and rejected earlier:* manual nudging by eye, with a city Opacity slider and a 0.5 mm / 0.1° nudge pad. It was built, and the user found it ineffective for getting a close fit. One data point in its favor: the yaw the user set by eye (−92.4°) matched scan 3a's fit (−92.35°). The controls stay in the debug panel.
- *Not offered:* a bigger single marker. It doesn't fit the Field Unit dock's 50 mm guides (007).

**Device findings, first two-marker session** (2026-10-26, 3 keep-world locks; playbook §5–§6). These are findings, not decisions:
- **Spacing reads about 86 mm, not 96.35** (85.9, 86.3, 86.5; −10.4 ± 0.3 mm), on every lock. *Analyst's inference:* most likely paper placement, not print scale (a print-scale error that big would also lift the city 11–19 mm, which wasn't seen). The ruler check is pending.
- **The line heading isn't repeatable across locks.** Keep-world re-locks gave dheading −1.456° then +1.471° (each lock's own spread ±0.02°). The left marker's own heading wandered 2.6°; the right held within 0.09°. *Inference:* the left paper is curled or lifted, or seen more obliquely. Fails the ±0.3° target.
- **The fit yaw is still positive** (+3.49°, one scan), so the two-marker lock did not remove the constant positive yaw seen with one marker.
- Within-lock spread is tiny (±0.02–0.03°, ±0.13–0.52 mm), and the markers' height held to 0.3 mm across locks (used in 017).

**Familiar or new:** new for this project. Every earlier lock used one marker.

## 016 · Open hypotheses: LiDAR height snap and the front/back offset
*2026-10-26. Not decisions (A has since become decision 017; B is still open). Recorded so they aren't lost; each waits for device data. Source: alignment-analyst. The inferences are the analyst's.*

**A. The LiDAR height snap (011) may be raising the city by about 3 mm.**
- Evidence: the eight logged snaps were +3.9, +1.2, −3.0, +2.0, +0.6, +4.2, +10.4, +5.1 mm (mean about +3.1). On the 2 locks with a fit, the fit's height bias term (012) mirrored the snap about 1:1 in the opposite direction. Screenshot 4 shows a gray band of the physical model about 5 mm tall along the front, consistent with the city sitting high.
- Weakness: the 1:1 mirror rests on 2 locks, and the bias term also absorbs LiDAR's depth bias, so the two are confounded.
- Candidate fix: accept only `.existingPlaneGeometry` hits within a 5 mm gate, or drop the snap and keep the marker's height.
- **Outcome:** the first two-marker session re-framed it. Snaps were small (−2.4, +0.7, +1.3 mm), so "raises by ~3 mm" weakened, but the plane itself drifted 3.7 mm while the markers held to 0.3 mm. Acted on: the snap is removed (017).

**B. The ~3.3 mm front/back offset may be constant, not session bias.**
- Evidence: per-lock means of the fit's x were 3.1 and 3.5 mm on the two locks (scans in 012).
- If so, retiring the saved 3.3 mm correction in 014 was premature. The 10.4 mm hand nudge in the next session, the reason it was retired, is reported by the orchestrator but not in the measurements log, so it can't yet be weighed against the scans.
- Approval history: the user approved saving the 3.3 mm correction (012). It was retired as part of the 014 change; reinstating it is a change to a saved constant and needs the user's approval again.
- Waits for device data: the two-marker sessions will show whether an x offset persists.

## 017 · Height comes from the markers; the LiDAR table plane is log-only
*2026-10-27. **User-approved.** Implemented in `leveledPose` (`PROXY/MarkerLock.swift`); reviewer PASS. Supersedes the snap in 011; resolves 016-A.*

**Decision.** The city's height is the markers' own measured height: for a pair, the mean of the left and right marker heights; for a single-marker lock, that marker's height. The markers lie on the paper's top surface, so there is no offset. The LiDAR table plane is still raycast (`.existingPlaneGeometry` first, then `.estimatedPlane`) but never applied. Each lock logs `Height: marker …, plane …, diff … (not applied)` and ends with `height from markers; plane diff ±X mm`. Above 3 mm it logs a warning. Planes more than 15 mm off are taken as another surface (floor, shelf) and skipped.

**Evidence.** In one world frame, across three keep-world re-locks, the detected plane's height moved 3.7 mm (−197.6, −194.3, −193.9 mm), while the markers' mean height held to 0.3 mm (−195.3, −195.0, −195.3). The snap was adding the plane's noise to the city.

**Trade-off (flagged by the reviewer).** Without the snap, any marker depth or scale error now shows up as a height error. The per-lock **plane diff** is the watch signal. A diff that is consistently above 3 mm in the same direction points to marker depth or scale. The ruler check (the black square should be 50.0 mm) confirms or rules that out. *Inference:* the plane diff also absorbs the plane's own drift, so read it across locks, not from a single lock.

**Alternatives.**
- Keep the snap with a tighter gate (`.existingPlaneGeometry` only, within 5 mm; 016-A). Rejected: the gate doesn't fix the plane drifting 3.7 mm within its own range.
- Keep the snap as it was (011). Rejected for the reason above.
- Add a fixed height offset now. Deferred: the analyst suggests adding one only if 2-scan data show a constant.

**Familiar or new:** new. Every lock since 011 took its height from the LiDAR plane.

## 018 · Robust duplicate-marker guard
*2026-10-27. Implemented in `MarkerSampler.swift`, `MarkerLock.swift` and `ARViewContainer.swift`; reviewer PASS (33 numeric checks plus the reviewer's own cases). Follow-ups in progress (ios-builder).*

**Problem.** At launch on 2026-10-26, the marker PDF open on the laptop screen put a second copy of each marker in view. ARKit's anchor jumped between the two copies, and a pair locked from samples spread ±90 mm / ±0.64°. Its spacing error (−10.9 mm) was under the 15 mm gross-error limit, so nothing caught it.

**Decision.** A marker's samples must look like one marker, or no lock (single or pair) is made from them:
- Refuse if fewer than 80% of the marker's samples lie within 5 mm of their median position, or if its heading spread is above 0.5°.
- When the lock goes ahead, its position is the median of the inliers only.
- On a refusal, the app logs one warning (`lock refused: … inliers=…`), restarts the samplers, and shows the pill **"Marker seen twice? Hide extra copies"**. The pill clears about 1 s after no marker is seen (`seenTwiceTimeout`).
- Clean locks read ±0.6–0.8 mm and ±0.05–0.07°, so the limits leave about 6× margin. Every lock line now logs `inliers=` (and `L_inliers`/`R_inliers` in the PAIR line).

**Alternatives.**
- Limit the RMS position spread. Rejected: it would catch the launch lock (±90 mm), but one stray sample (the untracked first detection, a re-acquisition jump) blows up the RMS, so it would also false-refuse an otherwise clean lock. The inlier fraction barely moves for one stray sample (one 28 mm off in 30 is 97%), while two copies split the samples roughly in half.
- Rely on the gross-error limit (014). Rejected: the duplicate lock passed it.

**Follow-ups in progress (ios-builder, not yet reviewed):** a NaN guard; a plane offset for the Field Unit (its dock marker isn't on the table); `plane_dy_mm` in the RELOCK line; and an escape when only the right marker keeps being refused: after 2 refusals the lock falls back to the left marker.

**Familiar or new:** new. No earlier lock checked sample consistency.

## 019 · Viewpoint-diverse sampling: built, tested, off by default
*2026-10-27. Explorer path (c), approved by the user. Built (`ViewpointSet.swift`, `MarkerSampler.swift`). Session 7 A/B on the Pin block. Off by default (`DIVERSE_SAMPLING = false`); the runtime toggle stays for future tests.*

**Decision.** Samples are accepted only across camera viewpoints: at least 2 cm or 3° from the last accepted sample, 0.18–0.45 m from the marker, incidence ≤50°, weighted by cos², with 12 viewpoints over a span of at least 15°. If that doesn't fill within 6 s, the lock falls back to the last 30 consecutive samples. The debug panel's **Sweep while locking** toggle turns it on at runtime. The default stays off, because round B did not beat round A.

**Evidence (session 7, Pin block).**
- Round A, consecutive: re-lock |dheading| 0.202° and 0.039°; anchor moves 2.16 and 0.70 mm; position spread 0.1–0.6 mm. Round A is the first session to pass the 0.3° repeatability target.
- Round B, diverse: |dheading| 0.404° and 0.948° (the second was a fallback, with a 9.2 mm anchor jump); position spread 1.9–3.5 mm; right-marker inliers 0.92–0.93; spacing −4.1 to −4.3 mm on two locks; plane diff up to −6.2 mm.
- **Confound:** the diverse locks were taken from 325–419 mm away, against 184–267 mm for the consecutive ones. The two rounds differ in distance as well as in sampling, so this A/B cannot separate the two effects.

**Alternatives.**
- Leave it on. Rejected for now: heading was worse (0.404° and 0.948° against 0.202° and 0.039°), position spread was about 10× larger, and the plane diff was worse.
- Repeat the test at matched distance before deciding. Not done. It is the open question, and the toggle is kept so the test can be run.

**Familiar or new:** new. Every earlier lock averaged 30 consecutive detections.

## 021 · Demo procedure for the 2026-10-28 critique
*2026-10-27. Plan, not yet run. The Field Unit 100 steps depend on a print that hasn't been made.*

**Decision.**
- **Field Unit 100:** the single 100 mm DockMarker, printed at 100% on a stiff card. Report the card's thickness: `DOCK_MARKER_TO_ORIGIN` assumes 1.2 mm (at least 1 mm board, plus paper and glue) on the dock's 1 mm corner guides, and a thicker board lowers the offset's y by its extra thickness (`PlacementSettings.swift`).

**Alternatives.** Not recorded at the time. The plan follows from the session 7 numbers in 019: Re-lock moves of 0.7–9.2 mm show that moving or re-scanning after a lock is the main drift risk, and the dock's 1.2 mm stack assumption is why the card's thickness has to be measured.

**Familiar or new:** new. No earlier session had a demo procedure.

## 022 · Subagent models: pass the role's frontmatter model
*2026-10-27. Process decision. ios-builder is on opus until after the critique.*

**Decision.** A role run through a general-purpose agent must pass the role's `model:` from its frontmatter on the Agent call. Otherwise the agent inherits the main session's model. ios-builder is set to opus until after the critique. CLAUDE.md (Agents) and `docs/HANDOFF.md` §1 say the same.

**Familiar or new:** new in practice. The frontmatter models predate this entry; passing them on each call is the new rule.
